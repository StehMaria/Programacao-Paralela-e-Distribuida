# Concorrência vs. Paralelismo, Escalonamento e Afinidade de CPU (Thread Affinity)

Compreender a diferença conceitual e prática entre concorrência e paralelismo, entender como o escalonador do Sistema Operacional distribui tarefas pelos núcleos do processador e aprender a utilizar técnicas de **Afinidade de CPU (*CPU Pinning*)** para maximizar o desempenho e a localidade de cache em aplicações de alto desempenho.

---

### 1. Concorrência vs. Paralelismo: O Grande Mal-Entendido

No desenvolvimento de software, é extremamente comum ver os termos **Concorrência** e **Paralelismo** serem usados como sinônimos. No entanto, em computação de alto desempenho (HPC), eles representam conceitos fundamentalmente distintos.

> *"Concorrência é sobre **estruturar** um programa; Paralelismo é sobre **executar** múltiplos processos simultaneamente."*

---

### 1.1 A Analogia do Chefe de Cozinha

Para fixar essa diferença de forma inesquecível, imagine a cozinha de um restaurante refinado:

* **Concorrência (Lidar com várias coisas ao mesmo tempo):**
  Imagine um **único chefe de cozinha** que precisa preparar 3 pratos diferentes: um risoto, uma carne grelhada e uma sobremesa. Ele coloca a água do risoto para ferver. Enquanto a água esquenta, ele tempera a carne. Em seguida, dá uma mexida no risoto, coloca a carne na frigideira e vai bater o creme da sobremesa. 
  O chefe está lidando com 3 tarefas ao mesmo tempo (**concorrência**), mas em nenhum instante físico ele possui 4 mãos. Ele fica **alternando o foco** rapidamente entre as panelas.

* **Paralelismo (Fazer várias coisas ao mesmo tempo):**
  Agora imagine a mesma cozinha, mas com **3 chefes de cozinha trabalhando lado a lado**. O Chefe 1 prepara exclusivamente o risoto, o Chefe 2 grelha a carne e o Chefe 3 bate a sobremesa. 
  Os 3 pratos estão sendo fisicamente preparados **no mesmo milissegundo** (**paralelismo**).

---

### 1.2 Tabela Comparativa Prática

| Aspecto | **Concorrência** | **Paralelismo** |
| :--- | :--- | :--- |
| **Foco Principal** | **Estrutura do código.** Como decompor o problema em tarefas independentes. | **Execução no Hardware.** Como rodar tarefas simultaneamente em múltiplos *cores*. |
| **Requisito de Hardware** | Pode rodar em **1 único núcleo** de CPU via intercalação de tempo. | Exige **múltiplos núcleos**, múltiplos soquetes ou GPUs. |
| **Mecanismo** | *Time-slicing* (divisão de fatias de tempo pelo Sistema Operacional). | Execução física simultânea nos circuitos dos núcleos. |
| **Objetivo Primário** | Modularidade, reatividade da interface, não bloquear no I/O. | **Desempenho e Vazão (Throughput).** Reduzir o tempo total de execução (*wall-clock time*). |

>Todo programa paralelo é concorrente, mas nem todo programa concorrente é paralelo!

### 2. O Escalonador do Sistema Operacional (OS Scheduler)

Quando escrevemos um programa com 16 *threads* em um computador que possui apenas 4 núcleos físicos, como o Sistema Operacional consegue executar tudo?

Através do **Escalonador (*Scheduler*)** do Kernel (no Linux, o famoso *Completely Fair Scheduler* - CFS).

![Imagem15](./imagens/15.jfif)

### 2.1 Como Funciona o Escalonamento Preemptivo
1. **Preempção:** O Kernel interrompe forçadamente uma *thread* em execução após ela esgotar sua fatia de tempo (*time slice* ou *quantum*, tipicamente entre 1ms e 10ms).
2. **Troca de Contexto (*Context Switch*):** O Kernel salva o estado dos registradores, ponteiro de instrução (`PC`) e pilha da *thread* atual e carrega o estado da próxima *thread* da fila de prontos.
3. **Re-escalonamento:** O núcleo físico passa a executar o código da nova *thread*.

---

### 2.2 O Problema do "Core Hopping" (Saltos entre Núcleos)

Por padrão, o escalonador do SO busca manter a carga de trabalho equilibrada entre todos os núcleos (*load balancing*). Se o Núcleo 0 estiver muito ocupado e o Núcleo 2 ficar ocioso, o Kernel pode mover a *Thread A* do Núcleo 0 para o Núcleo 2 na próxima fatia de tempo.

Embora isso garanta equidade, para programas de computação de alto desempenho isso é um **desastre de desempenho**!

#### Por que o *Core Hopping* destrói o desempenho?
Quando uma *thread* salta do Núcleo 0 para o Núcleo 2:
1. **Perda de Localidade de Cache (Cache Invalidation):** Toda a memória Cache L1 e L2 do Núcleo 0 que continha os dados da *thread* fica para trás.
2. **Cache Cold no Novo Núcleo:** O Núcleo 2 não possui nenhum dado dessa *thread* em sua L1/L2. A *thread* sofre uma avalanche de **Cache Misses**, sendo obrigada a recarregar tudo da L3 ou da memória RAM.
3. **Tráfego de Coerência de Cache:** As caches do Núcleo 0 precisam ser invalidadas e sincronizadas.

### 3. Afinidade de CPU (*Thread Affinity* / *CPU Pinning*)

Para impedir que o Sistema Operacional mova nossas *threads* livremente entre os núcleos, utilizamos a técnica de **Afinidade de CPU** (também conhecida como *CPU Pinning* ou *Ancoragem de Threads*).

> **Afinidade de CPU** é a associação explícita entre uma *thread* (ou processo) e um núcleo físico (ou conjunto de núcleos) específico do processador.

![Imagem17](./imagens/17.jfif)

---

### 3.1 Os 3 Grandes Benefícios da Afinidade de CPU

1. **Maximização da Reutilização de Cache (Cache Warmth):** Os dados lidos pela *thread* permanecem nas caches L1 e L2 do núcleo onde ela está ancorada.
2. **Respeito à Arquitetura NUMA:** Em servidores com múltiplos soquetes, ancorar uma *thread* no Soquete 0 garante que ela acesse apenas a memória RAM local do Nó NUMA 0 (evitando a travessia pelo barramento inter-soquete UPI/Infinity Fabric).
3. **Isolamento de Cargas de Trabalho:** Podemos "reservar" núcleos específicos para a nossa aplicação paralela e mover as tarefas secundárias do SO para outros núcleos.

---

### 4. Como Configurar a Afinidade na Prática

Podemos aplicar a afinidade de três formas: via linha de comando no Linux, via código C nativo (POSIX) e via variáveis de ambiente no OpenMP.

---

### Método 1: Linha de Comando no Linux (`taskset` e `numactl`)

Se você já possui um programa compilado e deseja definir a afinidade sem alterar o código fonte:

#### Usando `taskset` (Especifica a máscara de CPUs)
```bash
# Executa o programa 'meu_programa' utilizando APENAS os núcleos 0 e 1
taskset -c 0,1 ./meu_programa

# Executa o programa utilizando os núcleos de 0 a 3
taskset -c 0-3 ./meu_programa
```

#### Usando `numactl` (Especifica núcleos e nó NUMA de memória)
```bash
# Executa o programa nos núcleos do Nó NUMA 0 e aloca memória APENAS na RAM local do Nó 0
numactl --physcpubind=0-7 --membind=0 ./meu_programa
```

---

### Método 2: Código C Nativo no Linux (`pthread_setaffinity_np`)

A API POSIX de threads no Linux oferece a função `pthread_setaffinity_np()` para definir o conjunto de CPUs (*cpu_set_t*) ao qual uma *thread* ficará vinculada.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <sched.h>
#include <unistd.h>

#define NUM_THREADS 4

void* tarefa_thread(void* arg) {
    long id = (long)arg;
    
    // 1. Criar a estrutura do conjunto de CPUs (mask)
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);          // Limpa a máscara
    CPU_SET(id, &cpuset);       // Adiciona o Núcleo físico igual ao ID da thread

    // 2. Aplicar a afinidade para a thread atual
    pthread_t thread_atual = pthread_self();
    int s = pthread_setaffinity_np(thread_atual, sizeof(cpu_set_t), &cpuset);
    if (s != 0) {
        perror("Erro ao definir afinidade");
    }

    // 3. Verificar em qual núcleo a thread está rodando no momento
    int cpu_atual = sched_getcpu();
    printf("[Thread %ld] Ancorada com sucesso no Núcleo Físico %d\n", id, cpu_atual);

    // Simula processamento intenso
    unsigned long long soma = 0;
    for (unsigned long long i = 0; i < 1000000000ULL; i++) {
        soma += i;
    }

    return NULL;
}

int main() {
    pthread_t threads[NUM_THREADS];

    printf("Iniciando %d threads com afinidade de CPU estrita...\n", NUM_THREADS);

    for (long i = 0; i < NUM_THREADS; i++) {
        pthread_create(&threads[i], NULL, tarefa_thread, (void*)i);
    }

    for (int i = 0; i < NUM_THREADS; i++) {
        pthread_join(threads[i], NULL);
    }

    printf("Todas as threads concluíram o trabalho!\n");
    return 0;
}
```

### Método 3: Afinidade no OpenMP (`OMP_PROC_BIND` e `OMP_PLACES`)

No OpenMP, definir afinidade de *threads* é surpreendentemente simples e não requer uma única linha de código C — basta configurar variáveis de ambiente antes de rodar o programa!

#### Variáveis de Ambiente OpenMP:
1. `OMP_PROC_BIND`: Controla como as *threads* são vinculadas aos núcleos.
   * `true`: Ativa o vínculo de afinidade.
   * `spread`: Espalha as *threads* o máximo possível entre os soquetes (ideal para maximizar largura de banda de memória).
   * `close`: Agrupa as *threads* em núcleos vizinhos (ideal para compartilhar Cache L3).
2. `OMP_PLACES`: Define a granularidade das posições físicas.
   * `cores`: Cada *thread* é ancorada a um núcleo físico.
   * `threads`: Ancorada a um processador lógico (Hyper-Threading).
   * `sockets`: Ancorada a um soquete inteiro.

#### Exemplo de Execução no Terminal:
```bash
# Compilar a aplicação OpenMP
gcc -O3 -fopenmp programa_openmp.c -o programa_openmp

# Configurar afinidade: Espalhar 4 threads entre os núcleos físicos
export OMP_NUM_THREADS=4
export OMP_PROC_BIND=spread
export OMP_PLACES=cores

# Executar
./programa_openmp
```

---

### 5. Resumo e Boas Práticas

1. **Concorrência é Arquitetura; Paralelismo é Execução:** Concorrência estrutura o código para lidar com múltiplas tarefas; Paralelismo usa múltiplos núcleos físicos para rodar tudo simultaneamente.
2. **Cuidado com o *Core Hopping*:** Permitir que o Kernel do SO mova *threads* entre núcleos aleatoriamente causa *Cache Misses* massivos e destrói o desempenho em HPC.
3. **Use Afinidade de CPU (*CPU Pinning*):** Ancorar *threads* em núcleos fixos garante que a Cache L1/L2 permaneça "quente" com os dados do programa.
4. **Respeite a Arquitetura NUMA:** Sempre combine a afinidade de CPU com a alocação de memória local ao nó NUMA onde a *thread* reside.
